## 1. 为什么要改上游的阶段 3

上游阶段 3 写的是「`.mca` 解析 → 网格化 → 烘成 chunk Mesh 资产 → Addressables 加载」。本次需求放宽，实际只要求三件事：

1. **能读到地图信息**（方块在哪里、是什么）；
2. **能成为 Unity 的实体数据**（能在 Scene 里看到、能被相机漫游）；
3. **手机能加载默认内置地图**。

据此，把"PC 烘 Unity 资产"降级为"PC 出规范化数据、手机读数据"。带来的变化：

| 项 | 上游方案 | 本规划 | 理由 |
|---|---|---|---|
| 手机端 NBT 解析 | 不做 | 仍不做 | 一致 |
| 中间产物 | Unity Mesh/.asset | 自定义二进制 `.vxcell` | 与引擎解耦，UE 也能用（报告里"为地学所用"可复用） |
| 网格化位置 | PC（Editor 烘焙） | 手机运行时 C# | 省掉 AssetBundle/Addressables 打包链路，改数据不用重打包 |
| 分块加载 | Addressables | `StreamingAssets` + 自己写的 LRU 流式 | 数据仅 ~4 MB，不值得引入 Addressables 的版本风险 |
| 光照 | 烘焙/顶点色 | 顶点色 + 方向光 | 与上游一致 |

> 代价说明：手机端运行时网格化会比读现成 Mesh 多一点 CPU（每 chunk 数毫秒）。以本数据规模（841 chunk、峰值可见 ~81 chunk）完全可接受，且换来"改数据不重打包"的调试便利。

## 3. 关键实测数据（后面所有预算都基于它）

用 `voxel_tools/inspect_world.py` + `estimate_mesh.py` + `estimate_band.py` 对 A 存档逐 chunk 解码测得：

| 指标 | 数值 |
|---|---|
| 满地形 chunk | 841（= 29×29） |
| 覆盖范围 | chunk X −16..12，Z −14..14 → 方块 X −256..207，Z −224..239（**464×464 格**） |
| 地表 y 范围 | −64（基岩）~ 303（山顶）；平原 y=62 |
| 非空气方块总数 | 37,129,674 |
| 暴露面（全实体，含 chunk 边界重复面） | 6,984,959，均值 8305/chunk |
| 暴露面（地表 band=4） | 1,369,895，均值 1629/chunk |
| 暴露面（地表 band=8，**推荐**） | 1,785,959，均值 2124/chunk |
| 暴露面（仅高度图 1 面/列） | 1,112,230，均值 1322/chunk |
| 打包体积（只存 0/1 实体掩码 + zlib，理论下限） | 78.84 MB 原始 → **0.67 MB**，0.8 KB/chunk |
| 打包体积（**v1 正式格式**：方块 id + 局部调色板，deflate） | 22.96 MB 原始 → **3.95 MB**，4.8 KB/chunk |

**结论：数据 4 MB，体积不是瓶颈；瓶颈是三角面数。**（0.67 MB 那行是"只需知道实心/空气"时的下限；要带方块 id 出颜色，就得付 4 MB。）

按"每 chunk 面数 × 可见 chunk 数 × 2"估算三角面：

| 策略 | 半径 3（49 chunk） | 半径 4（81） | 半径 6（169） |
|---|---|---|---|
| 全实体（8.3k 面/chunk） | 81 万 | **135 万** | 281 万 |
| band=8（2.1k 面/chunk） | 21 万 | **34 万** | 72 万 |
| 高度图（1.3k 面/chunk） | 13 万 | 21 万 | 45 万 |

旗舰机（天玑 9400+）在简单 URP 顶点色 shader 下 70 万三角 / 169 draw call 是可以冲 60fps 的，但**全实体模式在半径 4 就已经 135 万三角，不可取**。所以：

- **近景（半径 ≤4）**：band=8 体素网格 → 34 万三角，安全；
- **远景（半径 4~10）**：直接用 chunk 内高度图出"梯田"网格 → 45 万三角覆盖 169 chunk；
- 阶段 4 若要再省，band 降到 4 或远景只留高度图。

> 高度图网格的"侧面"按 1 格高度差各出 1 个四边形，实测 1322 面/chunk，与 band=4 接近。远景用它够用，因为远处看不到崖壁细节。

## 4. 读取工具设计与格式规范

### 4.1 选型

| 方案 | 结论 |
|---|---|
| **自写 Python**（`struct`+`zlib`/`gzip`） | ✅ 采用。零依赖、离线可用；NBT/palette/位解包已在本规划的原型里跑通 |
| `amulet-core` / `nbtlib` / `anvil-parser`（pip） | 备选。要联网装包，且仍要写"转成自定义格式"的胶水，收益不明显 |
| `MCA Selector`（GUI） | 只能裁剪/删 chunk，不能导出体素 |
| 现成 "mca2obj" 类脚本 | 输出 OBJ，体积大、无法 LOD/流式，不符合"Unity 实体数据"要求 |

结论：**自写**，代码量约 500 行，其中 NBT reader 已在 `voxel_tools/inspect_world.py` 验证（2601 chunk / 0 error）。

### 4.2 工具 CLI

```bash
python vxtool.py scan    --world "<存档目录>"                 # 只统计，出 report.json
python vxtool.py build   --world "<存档目录>" --out "<输出目录>" \
                         --cell 8 --band 8 --only-full       # 生成 manifest + blocks + cells
python vxtool.py validate --dir "<输出目录>"                  # 结构/CRC/自洽校验
python vxtool.py dump    --dir "<输出目录>" --chunk 0,0 --y 60..64   # 文本调试视图
```

输出目录（`build`）：

```
out/
  world.manifest.json      # 元信息 + cell 索引表
  blocks.json              # 方块调色板（颜色/透明/中文名）
  cells/c0.0.vxcell …      # 16 个 cell 二进制
  report.json              # 每个 chunk 的方块数/面数/高度范围，供 Unity 侧对数
```

### 4.3 `world.manifest.json`

```json
{
  "formatId": "vxworld/1",
  "name": "新的世界",
  "source": { "mcVersion": "1.20", "dataVersion": 3463, "seed": 3717972541989053709,
              "regionMd5": ["900BAF…", "E13B2B…", "14BAF0…", "0D827B…"] },
  "axes": { "up": "Y", "mapping": "minecraft(x,y,z) -> unity(x,y,z) 同号直接映射",
            "blockSizeMeters": 1.0 },
  "bounds": { "chunkX": [-16, 12], "chunkZ": [-14, 14],
              "blockX": [-256, 207], "blockZ": [-224, 239],
              "blockY": [-64, 319], "surfaceYRange": [-64, 303] },
  "spawn": { "block": [-16, 63, 16], "chunk": [-1, 1] },
  "cellSize": 8,
  "blocks": "blocks.json",
  "cells": [
    { "file": "cells/c0.0.vxcell", "cellX": 0, "cellZ": 0,
      "chunkX": [-16, -9], "chunkZ": [-14, -7], "chunks": 64, "bytes": 51234, "md5": "…" }
  ]
}
```

约定：

- **坐标**：Minecraft 右手系（X 东、Y 上、Z 南）→ Unity 左手系。本规划采用**同号直接映射**，不做 Z 取反：这是最快、最不容易出绕序 bug 的做法；代价是世界在南北方向上是镜像的。本场景无文字、无导航语义，可接受。若之后要跟 MC 截图逐像素对照，再改成 `unity.z = -blockZ` 并同步翻转三角绕序。
- **单位**：1 方块 = 1 米。地图 464 m × 464 m，相机 `moveSpeed = 3`（现有 `CameraRig`）走完对角约 3.6 分钟，合理。
- **世界原点**：block(0,0,0) 就是 Unity(0,0,0)，不改整体偏移。

### 4.4 `blocks.json`

```json
{ "formatId": "vxblocks/1",
  "blocks": [
    { "id": 0, "name": "minecraft:air",      "solid": false },
    { "id": 1, "name": "minecraft:stone",    "zh": "石头",   "color": "#8A8A8A", "solid": true },
    { "id": 2, "name": "minecraft:deepslate","zh": "深板岩", "color": "#575757", "solid": true },
    { "id": 3, "name": "minecraft:water",    "zh": "水",     "color": "#3F76E4", "solid": false,
      "translucent": true }
  ] }
```

规则：

- `id` 0 固定为空气；其余由工具按"出现频次降序"分配，保证高频方块 id 小、`bitsPerBlock` 稳定。
- `solid=false` 的方块（空气/水/草/花/藤）**不参与网格化**（水直接不留面，避免整片湖面出百万级面）。这是本阶段最重要的取舍：水面/植被不渲染。
- 未知方块（换存档到模组世界时）→ 兜底 `{"color":"#808080","solid":true}`，并在 `report.json` 里列出，不静默失败。
- 颜色表：78 种方块手填一次（半天内可完成），颜色取原版材质平均色，用于顶点色。

### 4.5 `.vxcell` 二进制（v1，小端）

```
┌ cell header (32 B，明文)
│  0  char[4]  "VXC1"
│  4  u16      version = 1
│  6  u16      headerBytes = 32
│  8  i32      cellX, cellZ
│ 16  i32      chunkCount
│ 20  i32      paletteCount      (= blocks.json 里 solid 方块数)
│ 24  u32      flags             (bit0=1: payload 已 deflate)
│ 28  i32      payloadBytes      (压缩后长度)
├ payload = chunk index + chunk data（整体 deflate）
│  chunk index (chunkCount × 16 B)
│   i8  cx, cz (0..7)   u8 flags(bit0=hasData)  u8 sectionCount
│   i32 dataOffset (相对数据区)  i32 dataLength  i32 solidBlocks
│  chunk data (每 chunk 变长)
│    i16 minSectionY            // = -4 表示 y 起点 -64（-64/16）
│    u8  sectionCount
│    i16 topY[256]              // 每列最高实体方块 y，空列为 -32768；供 LOD1 高度图直接使用
│    section × sectionCount:
│      u8  mode                 // 0=全空气 1=全同方块 2=位压缩
│      u16 blockId              // mode==1
│      u8  bits                 // mode==2，= max(4, ceil(log2(palN)))
│      u16 palN                 // mode==2，该 section 局部调色板大小
│      u16 pal[palN]            // 局部调色板 → 全局 blockId
│      u8  packed[ceil(4096*bits/8)]   // LSB-first，同 MC 布局 index=(y*16+z)*16+x
└
```

要点：

- **section uniform 标记**是压缩的基础：实测每 chunk 平均 24 个 section，其中 13 个需要位压缩（地表以下含矿石/洞穴/水），另 11 个各占 1 字节。
- **整 cell 再 deflate 一层**：原始 22.96 MB → 3.95 MB。Unity 侧用 `System.IO.Compression.DeflateStream`（IL2CPP 自带，无原生依赖），每 cell 解压 ~1.4 MB、耗时数毫秒。
- `topY[256]` 每 chunk 512 B，841 chunk 合计 430 KB，换来远景 LOD 只需读每个 chunk 头部、不用解整份体素。
- `report.json` 记录每 chunk：`solidBlocks`、`faces(band=8)`、`minY/maxY`，Unity 侧对数用。

### 5.2 读取（Android 关键点）

`StreamingAssets` 在 APK 里是 jar 内的路径，**`File.ReadAllBytes` 读不到**。统一走：

```csharp
using (var req = UnityWebRequest.Get(Path.Combine(manifestUrl, cell.file)))
{ yield return req.SendWebRequest(); var bytes = req.downloadHandler.data; }
```

manifest 本身小，放 `Resources/` 或 `StreamingAssets` 都行；建议放 `StreamingAssets` 保持"数据整包可替换"。cell 读到 `byte[]` 后先 `DeflateStream` 解压到内存，再解析 index 与 chunk。

### 5.3 网格化（`ChunkMesher`）

1. 解码 chunk → `byte[] voxels` (sectionCount×4096) + `topY[256]`。
2. **band 裁剪**：对每列只保留 `topY = top - band + 1 .. top` 的实心方块（band 默认 8，可在 manifest 调）。
3. 6 邻居检查（同 chunk 内），空气/非实心邻居才出 quad；**chunk 边界暂不做邻块剔除**——那两面被埋在地下，不可见，代价约 10%，换来流式加载不需要 3×3 邻块依赖。
4. quad → 4 顶点（位置 + 法线 + 顶点色）、6 索引；`mesh.indexFormat = UInt32`（chunk 顶点 8k~34k，但留余量防爆）。
5. 顶点色 = `blocks.json` 里该方块颜色 × 面朝向明暗（`+Y` 1.0 / `±X` 0.8 / `±Z` 0.65 / `-Y` 0.5），一次性烘进顶点色，shader 只做简单光照。
6. 每 chunk 一个 `GameObject` + `MeshFilter` + `MeshRenderer`，位置 = `chunkOrigin`，bounds 自动参与视锥剔除。

### 5.4 流式（`ChunkStreamer`）

- 相机所在 chunk → 目标加载集合 = 半径 R 内的 chunk（R 默认 4，HUD 可调 2~6）。
- 每帧最多解 1 个 chunk（预算 ~5 ms），按距离排序；加载完成前该区域为空（有雾遮）。
- 卸载：超出 R+2 的 chunk 立刻 `Destroy` + `mesh.Clear()`（防泄漏）。
- 远景 LOD1（高度图网格）：阶段 3 **先不做**，但格式已备好（`topY`），阶段 4 直接接。

### 5.5 视觉

- 相机 `farClipPlane = 200`，`RenderSettings.fog` 线性 40→160，雾色接近天空色，盖住加载边界。
- 光照：单方向光（现有场景已有）+ 环境光，无实时阴影（体素阴影在移动端性价比低）。
- 水面/植被不渲染：湖会变成"干坑"，这是已知且接受的取舍（报告里写明）。

## 6. 任务拆解（P0–P8）

> 工时按"AI 生成 + 人验证"估；合计约 **14.5 小时**，P1/P2 可并行，落在 2 天（16 h）预算内。
> 每单元沿用上游模板：【单元】【输入】【输出】【约束】【验收】【不做】。

### P0 源数据落盘与基线（0.5 h）

- 【输入】D 盘存档 4 个 `.mca` + `level.dat`
- 【输出】`Tools/vxworld/data/source.json`（路径 + MD5 + 版本）；`voxel_tools/` 三个原型脚本归档进工程
- 【验收】MD5 与 §2.3 一致；`scan` 能复现 841 / 2601 / 78 这三个数
- 【不做】不复制 `.mca` 原件（保持只读，避免 16 MB 冗余）

### P1 方块颜色表 `blocks.json`（1.5 h）

- 【输入】`scan` 输出的 78 种方块名单 + 出现频次
- 【输出】`blocks.json`：id、name、中文名、颜色、solid、translucent
- 【验收】78 种全部有条目，无 `unknown`；Unity 侧读入后无重复 id
- 【不做】不做材质图集、不做逐面贴图

### P2 工具主程序 `vxtool.py`（3 h）

- 【输入】`world.manifest` 参数、存档目录
- 【输出】`build` 子命令：扫描 → 只保留 `Status=minecraft:full` → 逐 chunk 解 `block_states` → 写 `.vxcell` + manifest + report
- 【约束】纯标准库；单线程即可（841 chunk 实测 1~3 分钟）；输出确定性（同输入同 MD5）
- 【验收】输出 16 个 cell、841 chunk、总体积 ≤ 5 MB（实测 3.95 MB）；`report.json` 里 faces 与 §3 实测值误差 <1%
- 【不做】不处理 Nether/End、不处理方块实体（箱子/告示牌）、不做 greedy meshing

### P3 校验器 + 文本调试（1 h）

- 【输入】`build` 输出目录
- 【输出】`validate`（magic/长度/CRC/索引越界/palette 越界）、`dump`（某一 chunk 某 y 层的 ASCII 切片）
- 【验收】故意改坏 1 字节能被 `validate` 报出并定位到 chunk；`dump` 输出与 MC 截图肉眼一致
- 【不做】不做跨版本兼容迁移

### P4 Unity 读取 + 网格化（3 h）

- 【输入】`StreamingAssets/vxworld/`
- 【输出】`VoxelWorld` / `VoxelPalette` / `VxCellReader` / `ChunkMesher` / `Voxel.mat` / `VoxelVertexColor.shader`
- 【约束】URP、IL2CPP、ARM64、`IndexFormat.UInt32`、单材质
- 【验收】编辑器 Play 出现地形：平原 y=62、山顶 y≈303、海平面高度正确；Console 打印 chunk/顶点数；无 NaN、无爆面
- 【不做】不做水面/植被、不做邻块剔除、不做碰撞体

### P5 流式加载（2 h）

- 【输入】P4 的读取能力 + 相机位置
- 【输出】`ChunkStreamer`：半径内加载、超距卸载、每帧 1 个 chunk 预算、异步 `UnityWebRequest`
- 【约束】单帧解码+网格化 ≤ 8 ms；常驻 chunk 数 ≤ (2R+3)²
- 【验收】编辑器里瞬移 300 m，chunk 增删数量与预期一致，无内存持续增长（Profiler 看 Mesh 数回落）
- 【不做】不做预取预测、不做 Addressables

### P6 默认内置地图接入（1.5 h）

- 【输入】`world.manifest.json` 的 spawn/bounds
- 【输出】启动即站在 spawn、可漫游；`CameraRig` 的移动范围夹在地图 bounds 内；`VoxelDebugHud`
- 【约束】APK 增量 ≤ 5 MB；冷启动到可操作 ≤ 3 s
- 【验收】真机装上后不操作就能看到地形；HUD 显示 chunk 数/三角数/加载 ms/朝向
- 【不做】不做菜单/地图选择（只有一张图）

### P7 验收与对数（1 h）

- 【输入】工具 `report.json` + Unity 运行时统计
- 【输出】`docs/stage3_acceptance.md`：三个数字对齐（chunk 数、总面数、抽 20 chunk 的方块数逐一对上）+ 截图
- 【验收】见 §8
- 【不做】不做 PerfDog 正式报告（阶段 4 做）

### P8 缓冲/降级（1 h）

- 按 §9 的降级顺序处理没达标项。

### 依赖与关键路径

```
P0 → P1 ─┐
P0 → P2 → P3 → P4 → P5 → P6 → P7
```
P1 与 P2 可并行；P4 是最大不确定项（网格化正确性），必须留出调试时间。

## 8. 验收标准（可量化）

| # | 项 | 阈值 | 怎么测 |
|---|---|---|---|
| A1 | 工具产出完整性 | 841 chunk / 16 cell / 0 error | `vxtool.py validate` 输出 |
| A2 | 数据体积 | 全量 ≤ 5 MB（实测 3.95 MB） | 输出目录求和 |

| A4 | 地形一致性 | 平原 y=62、最高点 y≈303、坐标轴方向正确 | MC 同角度截图 vs Unity 截图（允许南北镜像） |

| A9 | 鲁棒性 | 删掉 1 个 cell 文件后启动不崩，HUD 报缺块 | 手工删文件 |

## 9. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 1.20.1 的 `block_states` 字段与预期不符 | 低 | 解析失败 | 已实测 3463 可解析；`scan` 先打印根 tag；保留 `BlockStates` 大写回退 |
| 地表 band 裁剪后山体侧面出现"空腔" | 中 | 视觉瑕疵 | band 提到 12~16（面数 2.7k/chunk，仍可接受）；或只对陡坡放宽 band |
| 顶点数超 65535 | 低 | Mesh 报错 | `IndexFormat.UInt32` 强制开启 |
| Android 读 `StreamingAssets` 失败 | 中 | 无地形 | 统一 `UnityWebRequest`；加 `File.ReadAllBytes` 的编辑器分支并打日志区分 |
| 手机端网格化卡顿 | 中 | 顿挫 | 每帧 1 chunk 预算 + 距离排序；仍卡则把 band 降到 4 或先出高度图 LOD |
| 水面不渲染被误认为 bug | 中 | 验收争议 | 报告与 HUD 明写"水/植被不参与网格化"，截图注明 |
| 颜色表偏差大，像"灰模" | 中 | 观感差 | 先出灰模验证几何，再花 1 h 对 20 个高频方块调色 |
| 数据换成模组世界后一片灰 | 低 | 观感差 | `report.json` 列出未知方块；兜底色 + 提示 |
| 时间滑档 | 中 | 阻塞阶段 4 | 降级顺序见下 |

**降级顺序**（从轻到重）：

1. band 8 → 4（面数 −23%）；
2. 半径 4 → 3（面数 −40%）；
3. 去掉远景需求，只做半径 3 的固定区域；
4. 完全跳过流式：启动一次性加载 1 个 cell（64 chunk，约 27 万三角），只保留"能漫游"这一条验收；
5. 最差：只做"单 cell 静态展示 + 相机飞行"，数据管线保留、体验降级。

## 10. 明确不做（本阶段边界）

- 手机端不解析 `.mca`、不读 NBT；
- 不做 Nether / End / 模组维度；
- 不做实体、方块实体（箱子/告示牌/床）；
- 不做水面、植被、半透明（`solid=false` 一律不网格化）；
- 不做光照烘焙、不做实时阴影、不做图集贴图；
- 不做 greedy meshing（面数不够大，先不做）；
- 不引 Addressables / Burst（本数据规模用不上，避免装包风险）；
- 不做跨存档/多地图选择，只内置一张。
